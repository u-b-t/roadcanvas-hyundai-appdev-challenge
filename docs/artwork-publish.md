# 자유그림 작품 공개

이름을 붙인 자유그림을 다른 사용자가 볼 수 있는 작품으로 등록하는 앱 동작을 정리한다. 서버 계약은 [자유그림 공개와 투표 클라이언트 명세](firebase-artwork-client.md)를 따른다.

## 구조

- 화면은 `AppContainer.artworkPublisher`(`kr.roadcanvas.app.artwork.ArtworkPublisher`)만 쓰고, 결과 화면과 내 그림 상세는 `ArtworkPublishController`로 같은 상태와 조작을 공유한다.
- 서버 접근은 `ArtworkStore`, 작성자(UID·닉네임)는 `ArtworkAuthorProvider` 인터페이스 뒤에 둔다. 테스트는 `app/src/sharedTest/`의 `FakeArtworkStore`, `FakeArtworkAuthorProvider`로 연결 실패, 인증 실패, 청크 저장 실패, 저장되지 않은 청크를 주입한다.
- 익명 인증(#73)과 Firebase 연동(#74)이 연결되기 전에는 `DefaultAppContainer`가 항상 실패하는 `UnavailableArtworkStore`와 `UnavailableArtworkAuthorProvider`를 쓴다. 이 상태의 앱에서 공개를 누르면 계정 확인 실패로 표시된다.
- 기기 공개 기록은 Room `artwork_publication` 테이블(DB 버전 5)에 완료 기록별로 작품 ID와 마지막 공개 상태를 보관한다. 완료 기록을 지우면 함께 지워진다.

## 등록 흐름

1. 이름을 붙인 자유그림만 공개할 수 있다. 이름은 #78의 그림 이름을 쓰며 앞뒤 공백을 제거한 1~20자다. 동그라미 챌린지 기록은 공개하지 않는다.
2. "작품 공개하기"를 누르면 출발점·도착점을 포함한 경로, 닉네임과 작품 이름이 공개된다는 안내를 띄우고 "동의하고 공개"를 눌러야만 진행한다.
3. 작품 ID(UUID)가 없으면 만들어 등록 중 상태로 기기에 먼저 저장한다. 이후 재시도와 다시 공개는 이 ID를 계속 쓴다.
4. 작성자를 확인하고 닉네임(1~30자)을 검사한 뒤 `DRAFT` 문서를 저장한다.
5. 경로를 500점씩(약 5만 자) 나눠 `index` 0부터 청크로 저장한다. 좌표는 유한한 위경도 범위와 0 이상의 기록 시각인지 먼저 확인한다.
6. 저장된 청크의 index가 0부터 청크 수-1까지 빠짐없이 있는지 확인하고 `PUBLISHED`로 바꾼 뒤 기기에 공개됨을 저장한다.

어느 단계에서 실패해도 완료 기록은 그대로 두고 공개 상태만 실패로 저장한다. "다시 공개하기"는 동의를 이미 받았으므로 안내 없이 같은 작품 ID로 처음부터 다시 쓴다. 등록 도중 앱이 종료돼 등록 중 상태로 남은 기록은 다음 실행에서 실패로 보인다.

## 비공개 전환과 이름 변경

- 공개됨 상태에서 "비공개로 전환"을 누르면 문서를 `DRAFT`로 바꾸고 미공개로 저장한다. 실패하면 공개됨을 유지하고 이유를 보인다. 다시 공개하면 같은 작품 ID로 문서와 청크를 다시 쓴다.
- 공개 중에 이름을 바꾸면 공개 작품의 `title`도 바꾼다. 서버 반영에 실패하면 기기 이름은 바뀐 채 "공개 작품의 이름은 바꾸지 못했어요"를 보이며, 이름을 다시 저장하면 다시 반영한다. 미공개 작품은 다음 공개 때 바뀐 이름으로 등록한다.
- 공개 중이거나 등록 중인 작품은 내 그림에서 삭제할 수 없다. 기기 기록을 지우면 앱에서 비공개로 되돌릴 방법이 없어지기 때문이다. 비공개로 바꾼 뒤 삭제할 수 있다.

## 제약과 미검증 항목

- 익명 계정을 잃으면(앱 데이터 삭제, 재설치, 기기 변경) 기존 작품의 소유권을 복구할 수 없다. 새 UID로는 기존 작품을 비공개로 바꾸거나 이름을 바꿀 수 없다.
- 서버는 작품 영구 삭제를 제공하지 않는다. 비공개 전환은 다른 사용자의 조회만 막고 서버 데이터는 남는다. 미공개 작품의 기기 기록을 지워도 서버의 `DRAFT` 문서와 청크는 남는다.
- 닉네임 변경 시 기존 작품의 `nickname` 갱신은 이 작업에 포함하지 않았다([클라이언트 조회·프로필 계약](firebase-client-queries.md) 참고).
- 여러 쓰기는 원자적이지 않다. 청크 저장 뒤 확인 전에 끊기면 `DRAFT` 문서와 일부 청크가 남고, 다시 공개할 때 같은 문서를 덮어쓴다. 경로가 바뀌지 않으므로 남는 청크는 없다.
- 실제 Firestore와 익명 인증으로의 등록, 서버 규칙 거부 응답의 분류, 네트워크가 불안정한 차량 환경에서의 동작은 아직 확인하지 않았다. 상태 전환과 오류 처리는 단위 테스트와 대체 구현을 쓴 Cucumber 시나리오(`artwork_publish.feature`)로만 확인했다.
