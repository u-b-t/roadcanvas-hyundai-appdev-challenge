# 땅따먹기 소유권 모델 검증

[땅따먹기 서버 설계 전제](firebase-territory-planning.md)의 질문 중 영역 표현, 지도 범위 조회, 동시 변경을 Cloud Functions 없이 Firestore 규칙과 클라이언트 트랜잭션만으로 처리할 수 있는지 Firebase Local Emulator Suite에서 확인했다. 운영 Firebase(`roadcanvas-f9f2a`)에는 규칙·인덱스·데이터를 배포하거나 쓰지 않았다. 아래 컬렉션과 규칙은 계약 **후보**다. #103에서 후보 A를 채택해 게임 규칙과 함께 확정했고, 확정한 계약과 운영 규칙은 [서버 땅따먹기](firebase-territory.md)에 있다.

## 결론

- 격자 소유권(geohash 칸 하나 = 문서 하나)은 클라이언트 트랜잭션으로 동시 탈취, 중복 제출, 오프라인 재시도를 모두 일관되게 처리했다. 규칙이 칸 단위로 소유자·획득 기록·버전을 검사할 수 있다.
- 정확한 도형은 지도 조회 쿼리가 트랜잭션에 포함되지 않아, 색인 없이 조회 후 차집합을 쓰면 동시에 만든 도형이 겹친 채 저장되는 것을 재현했다. 지역 색인 문서를 트랜잭션에서 함께 읽고 쓰면 겹침이 없었지만, 규칙은 도형이 실제로 줄었는지나 획득 경로와 맞는지 검사할 수 없어 다른 사용자의 도형을 마음대로 바꾸는 요청을 막지 못한다.
- 첫 구현 후보는 **geohash7(서울 기준 약 121m x 152m) 격자 + 획득 기록 + 칸별 version 규칙 + 앱 재시도**다. 칸 크기는 기획 결정이 필요하다.
- 어느 방식도 서버가 경로·면적을 검증하지 않는다. 클라이언트가 보낸 획득 범위를 그대로 믿으므로 위조 방지가 필요하면 Cloud Functions나 별도 서버가 필요하다.

## 검증 실행 방법

검증 코드는 `firebase/territory-verification/`에 있다. Node.js와 Java 11 이상이 필요하다(확인 환경: Node 26.5.1, OpenJDK 21, firebase-tools 15.35.0, Firebase JS SDK 13.2.0). 이 디렉터리의 `firebase.json`은 Firestore(8180)와 Auth(9199) 에뮬레이터만 띄우고, 프로젝트 ID는 운영에 연결되지 않는 `demo-roadcanvas-territory`다. 규칙은 같은 디렉터리의 `territory.rules`를 쓴다.

```sh
cd firebase/territory-verification
npm ci
JAVA_HOME=/opt/homebrew/opt/openjdk@21 npm run verify
```

`npm run verify`는 `firebase emulators:exec`로 에뮬레이터를 띄워 `verify.mjs`를 실행하고 끝나면 에뮬레이터를 종료한다. 사용자 6명과 비로그인 사용자 1명을 Auth 에뮬레이터 익명 로그인으로 만든다. 각 항목을 `PASS`/`FAIL`로 출력하고, 마지막에 측정값을 `RESULTS` JSON으로 출력한다. 하나라도 실패하면 종료 코드가 1이다. 전역 `firebase` CLI가 Node 버전과 맞지 않으면(Node 26에서 전역 firebase-tools가 `SlowBuffer` 오류로 시작하지 않았다) 이 디렉터리의 고정 버전을 쓰는 `npm run verify`를 사용한다.

2026-11-09 맥북에서 세 번 실행해 매번 36개 항목이 모두 통과했다. 아래 수치는 첫 실행 결과이며, 재시도 횟수와 경합 실패 건수는 실행마다 달라진다(범위는 표에 함께 적었다).

## 영역 표현 비교

| 항목 | 정확한 도형 | 격자(geohash) |
| --- | --- | --- |
| 저장 | 소유 도형 문서에 MultiPolygon(JSON 문자열, Firestore는 중첩 배열 불가), 지역 색인 `cover` | 칸 문서 하나에 소유자, 획득 ID, version |
| 탈취 계산 | 기기에서 겹치는 도형마다 차집합. 도형이 쪼개지고 꼭짓점이 늘어난다 | 경로 안 칸 목록을 구해 소유자를 덮어쓴다 |
| 경계 정확도 | 주행 경로 그대로 | 칸 단위로 근사. 칸 중심이 경로 안에 있으면 획득하는 식의 규칙이 필요 |
| 동시 변경 | 지역 색인 문서를 함께 읽고 써야 직렬화된다(P1, P2) | 겹치는 칸 문서 자체가 충돌 단위다(G1) |
| 규칙 검증 | 소유자 필드와 version만 가능. 도형이 줄었는지, 남의 도형을 정당하게 깎는지 검사 불가 | 칸마다 본인 소유, 같은 요청의 본인 획득 기록에 포함, version +1을 검사 |
| 면적 집계 | 도형 면적 필드 합. 탈취당한 도형 갱신은 탈취자가 대신 쓴다 | 칸 수 x 칸 면적. `count()` 집계 |
| 한 번에 쓰는 양 | 겹친 도형 수 + 지역 문서 수 + 1 | 경로 안 칸 수 + 1 |
| 기기 구현 | 다각형 차집합 라이브러리(검증은 JS `polygon-clipping`) | geohash 인코딩만 필요 |

geohash 대신 S2 셀을 쓰면 칸 모양이 정사각형에 가깝고 위도에 따른 왜곡이 작지만 Android와 규칙 검증 양쪽에 S2 라이브러리와 셀 ID 규칙이 필요하다. 지역 미터 격자(예: 50m 고정 격자)는 계산이 쉽지만 좌표계를 따로 정의해야 한다. 이번 검증은 geohash로만 했다.

서울시청 부근 geohash 칸 크기(계산값):

| 정밀도 | 칸 크기 | 500m x 500m 영역의 칸 수 | 1km² 칸 수 |
| --- | --- | --- | --- |
| 6 | 약 969m x 607m | 0.4 | 2 |
| 7 | 약 121m x 152m | 13.6 | 54 |
| 8 | 약 30m x 19m | 435 | 1,740 |

geohash8은 한 블록 둘레를 돌기만 해도 수백 칸이 되어 한 트랜잭션의 쓰기 수와 지도 조회 읽기 수가 크게 늘어난다. geohash7은 도로 한 블록 정도의 해상도다.

## 지도 범위 조회 비용

Firestore는 쿼리가 돌려준 문서마다 읽기 1회를 과금하고, 결과가 없어도 쿼리당 최소 1회를 과금한다. `count()`는 읽은 인덱스 항목 1,000개당 1회다. 무료 한도는 하루 읽기 50,000회, 쓰기 20,000회다. `in`과 `array-contains-any`는 값 30개까지다. 참고: [가격](https://firebase.google.com/docs/firestore/pricing), [쿼리 제한](https://firebase.google.com/docs/firestore/query-data/queries), [한도](https://firebase.google.com/docs/firestore/quotas).

| 실측 | 결과 |
| --- | --- |
| G5 격자: geohash7 칸 1,600개(4명이 400개씩), 화면 약 1km x 600m | 화면을 덮는 geohash6 접두어 4개를 `where('gh6', 'in', [...])` 쿼리 1회로 조회, 문서 128개 읽음. 그중 화면 안 칸은 45개 |
| G5 사용자별 면적 | `where('ownerUid', '==', uid)` `count()`가 사용자마다 400을 반환. 400칸 x 18,395m² = 약 7.36km² |
| P3 도형: 150m 정사각형 100개(200m 간격) | `where('cover', 'array-contains-any', [접두어 4개])` 1회로 문서 63개 읽음. 그중 화면과 겹친 도형은 24개 |

- 격자에서 칸이 빽빽하게 소유되어 있으면 화면 하나의 읽기 수는 덮는 geohash6 칸 수 x 32(geohash7) 또는 x 1,024(geohash8)다. geohash7, 화면당 geohash6 4칸이면 최대 128회, geohash8이면 최대 4,096회다. 지도를 움직일 때마다 새 접두어만 추가로 읽는다.
- 읽기를 줄이려면 geohash6 칸마다 하위 칸 소유자 맵을 담은 요약 문서를 두는 방법이 있다. 화면당 읽기는 4회 정도로 줄지만, 같은 geohash6 안의 모든 획득이 요약 문서 하나를 갱신해 충돌하고, 맵 안 항목 단위 규칙 검증이 어려워진다. 이번에는 실측하지 않았다.
- 도형은 화면과 겹치는 도형 수만큼 읽지만, 도형 하나가 큰 영역을 덮거나 탈취로 꼭짓점이 늘면 문서가 커진다(문서 최대 1MiB). P2에서 탈취 후 최대 꼭짓점은 10개, JSON 403자였다. 실제 주행 경로는 수백 점이므로 단순화 기준이 필요하다.
- 사용자별 전체 순위는 `count()`로 만들 수 없다. 사용자별 면적 문서를 두면 탈취자가 피해자 문서를 감소시켜야 하는데 규칙이 감소량을 검증할 수 없다. 순위는 `count()` 재계산이나 서버 작업이 필요하다.

## 동시 탈취·중복 제출·오프라인 재시도 실측

격자 획득은 클라이언트 트랜잭션 하나로 처리한다. 트랜잭션이 획득 기록 `territoryCaptures/{captureId}`를 먼저 읽어 이미 있으면 아무것도 쓰지 않고, 없으면 칸을 모두 다시 읽어 소유자를 덮어쓰고 version을 1 올린 뒤 획득 기록을 만든다. 일관성 검사는 모든 칸이 자신을 포함한 가장 늦은 획득 기록을 가리키는지, 칸의 version이 그 칸을 포함한 획득 기록 수와 같은지(잃어버린 갱신이 없는지) 확인한다.

| 시험 | 결과 |
| --- | --- |
| G1 동시 탈취: A의 5x5 영역에 5명이 서로 겹치는 5x5를 동시에 3번씩(15건) | version 규칙 + SDK 기본 재시도(5회): 7건 성공, 8건 `permission-denied` 실패(세 번 실행에서 성공 6~9건). 실패한 건은 아무것도 쓰지 않았고 칸 상태는 일관적 |
| G1 같은 경합, 규칙에서 version 조건만 뺀 컬렉션 | 15건 모두 성공. SDK 시도 최대 5회(기본 상한에 도달한 건 있음) |
| G1 version 규칙 + 앱이 `permission-denied`면 트랜잭션을 다시 실행(최대 5번) | 15건 모두 성공, 앱 실행 최대 5번. 칸 상태 일관적 |
| G1 같은 9칸에 6명이 동시 제출, 앱 재실행 최대 10번 | 6건 모두 성공, 앱 실행 최대 6번. 마지막 커밋이 소유 |
| G2 중복 제출: B 획득 → C가 8칸 탈취 → B가 응답을 잃었다고 보고 같은 획득 ID로 다시 실행 | 획득 기록이 있어 아무것도 쓰지 않음. C가 빼앗은 8칸 유지 |
| G2 같은 획득 기록을 batch로 다시 생성, 이전 획득 기록을 재사용해 칸만 쓰기, 남의 UID로 획득 기록, 획득 기록 없는 칸, 획득 기록에 없는 칸, 비로그인 조회 | 모두 규칙에서 거부 |
| G3 오프라인 트랜잭션: B의 연결을 끊고(TCP 중계 차단) 획득 | SDK가 5번 시도 후 약 6.7초 만에 `unavailable`로 실패. 아무것도 쓰지 않음 |
| G3 오프라인 batch: 끊긴 상태에서 캐시의 version으로 batch를 만들고, 그동안 C가 같은 9칸 탈취, 재연결 | batch는 끊긴 동안 확정되지 않고 대기. 재연결 약 1.7초 뒤 오래된 version 때문에 `permission-denied`로 전체 거부. C 소유 유지, B의 획득 기록도 남지 않음 |
| G3 비교: version 조건 없는 컬렉션에 같은 오프라인 쓰기 | 재연결 후 B의 오래된 쓰기가 C의 최신 소유를 덮어씀(잃어버린 갱신 재현) |
| G3 재연결 후 같은 획득 ID로 트랜잭션 재실행 | 현재 소유자(C)를 다시 읽어 9칸 탈취. 한 번 더 실행하면 중복으로 처리 |
| G4 한 트랜잭션에 획득 기록 1개 + 칸 499개(칸마다 같은 획득 기록 `getAfter`) | 생성·탈취 모두 성공(에뮬레이터에서 약 0.3초). 후보 규칙의 칸 499개 제한으로 500칸은 거부 |
| P1 도형, 색인 없음: B·C가 동시에 주변 도형을 조회(빈 결과) 후 각자 트랜잭션으로 300m 정사각형 생성 | 두 도형이 22,500m² 겹친 채 저장됨 |
| P2 도형, geohash6 지역 색인 문서를 트랜잭션에서 읽고 version 증가: A의 400m 영역에 5명이 동시 획득(앱 재실행 포함) | 5건 모두 성공. 도형 간 겹침 0m², 저장 면적 합 291,000m²가 입력 도형 합집합 면적과 같음. 같은 획득 ID 재실행은 중복 처리 |

확인한 동작:

- **경합이 규칙 거부로 보인다.** 트랜잭션이 읽은 뒤 다른 트랜잭션이 칸을 바꾸면, 재시도 가능한 충돌 오류 대신 version 규칙 위반(`permission-denied`)으로 끝나는 경우가 있었다. SDK는 `permission-denied`를 재시도하지 않는다. version 조건을 뺀 컬렉션에서는 같은 경합이 모두 SDK 재시도로 성공했으므로 원인은 version 규칙이다. 그래서 앱이 `permission-denied`를 받으면 짧은 대기 후 같은 획득 ID로 몇 번 더 실행해야 한다. 진짜 규칙 위반이면 매번 거부되므로 횟수를 제한하고 최종 실패를 사용자에게 알린다.
- **version 규칙은 오프라인 대기 쓰기를 막는 데 필요하다.** SDK는 끊긴 동안의 batch를 대기열에 두었다가 재연결하면 보낸다. version 조건이 없으면 오래된 결과가 최신 소유를 덮어쓴다. 획득은 반드시 온라인 트랜잭션으로 보내고 오프라인 batch로 보내지 않는다. version 규칙은 이를 지키지 않은 쓰기를 거부하는 안전장치다.
- **오프라인에서는 트랜잭션이 실패한다.** 주행 중 연결이 끊기면 획득 결과(경로와 획득 ID)를 기기에 보관하고, 연결되면 같은 획득 ID로 트랜잭션을 다시 실행한다. 이때 칸 소유자는 다시 읽으므로 끊긴 동안의 다른 탈취를 반영한다. 기존 [완료 그림 등록](firebase-registration.md)처럼 Room에 미제출 획득을 남기는 방식이 맞다.
- `disableNetwork()`는 JS SDK 트랜잭션 RPC를 막지 않아(끊긴 상태에서도 트랜잭션이 성공했다) 오프라인 시험에 쓰지 않았다. 대신 B의 Firestore 연결을 로컬 TCP 중계로 연결하고 중계를 끊었다.

## 데이터 계약 후보

### 후보 A: geohash7 격자(권장)

| 경로 | 필드 |
| --- | --- |
| `territoryCaptures/{captureId}` | `ownerUid`, `createdAt`(서버 시각), `cells`(geohash7 문자열 1~499개), `cellCount`. 생성만 가능, 수정·삭제 불가. 획득 이력이자 중복 제출 식별자 |
| `territoryCells/{geohash7}` | `ownerUid`, `captureId`, `capturedAt`(서버 시각), `version`(생성 1, 이후 +1), `gh6`(문서 ID 앞 6자, 지도 조회용) |

- 규칙(`firebase/territory-verification/territory.rules`의 `territoryCaptures`, `territoryCells`): 칸 쓰기는 본인 UID, 같은 요청에서 만든 본인 획득 기록(`getAfter`로 확인, `createdAt == request.time`)에 이 칸이 포함, version +1일 때만 허용한다. 이전 획득 기록을 재사용하거나 남의 이름으로 쓰는 요청을 막는다.
- 앱 절차: 경로가 확정되면 획득 ID(UUID)와 칸 목록을 Room에 저장 → 온라인이면 트랜잭션 실행 → `permission-denied`는 제한 횟수만큼 재실행, `unavailable`은 연결 후 재실행 → 성공 또는 중복이면 기기 기록 정리.
- 사용자 면적: `count()`로 칸 수를 세 면적으로 환산한다. 순위표는 아직 없다.
- 트레이드오프: 경계가 칸 단위로 근사된다. 지도 조회가 칸 문서 수에 비례한다. 같은 칸을 동시에 노리는 차량이 많으면 재실행이 늘어난다(6명 동시 9칸에서 최대 6번). Firestore는 한 문서에 계속 높은 빈도로 쓰는 것을 피하라고 안내하므로 인기 지역의 실제 처리량은 별도 확인이 필요하다.
- 획득 이력은 획득 기록 컬렉션이 담당한다. 누구의 칸을 빼앗았는지 남기려면 획득 기록에 이전 소유자별 칸 수 같은 필드를 추가해야 하는데, 규칙으로 검증할 수 없어 클라이언트가 계산한 값이 된다. 보관 기간과 삭제 방법은 정하지 않았다.

### 후보 B: 정확한 도형 + 지역 색인

| 경로 | 필드 |
| --- | --- |
| `territoryShapes/{shapeId}` | `ownerUid`, `captureId`, `geometryJson`(MultiPolygon), `cover`(geohash6 30개 이하), `version` |
| `territoryRegions/{geohash6}` | `shapeIds`(500개 이하), `version` |
| `territoryShapeCaptures/{captureId}` | `ownerUid`, `createdAt` |

- 획득 트랜잭션은 새 도형이 걸친 지역 문서를 모두 읽어 후보 도형 ID를 얻고, 후보 도형을 읽어 차집합을 쓰고, 지역 문서의 version을 올린다. 지역 문서가 잠금 역할을 한다.
- 탈취당한 도형은 탈취자가 대신 갱신·삭제해야 하므로 규칙이 다른 사용자의 도형 수정을 허용해야 한다. 규칙이 도형 축소를 검증할 수 없어 임의 변경을 막지 못한다.
- 삭제된 도형 ID가 새 도형 범위 밖의 지역 문서에 남을 수 있어 읽는 쪽에서 없는 문서를 건너뛴다(검증 코드도 그렇게 처리했다).
- 큰 도형은 많은 지역에 걸쳐 트랜잭션이 읽고 쓰는 문서가 늘고, 같은 지역의 모든 획득이 지역 문서에서 충돌한다. 도형이 쪼개질수록 문서 크기와 기기 계산량이 늘어난다.

## 확인하지 못한 사항

- 운영 Firestore에서의 동작: 경합 시 `permission-denied`와 충돌 오류 중 무엇이 나오는지, 규칙의 `getAfter`를 칸마다 같은 문서로 499번 호출할 때 접근 횟수 제한(트랜잭션 20회, 캐시된 호출은 제외)에 걸리지 않는지는 에뮬레이터에서만 확인했다. 에뮬레이터는 규칙 없는 컬렉션에 쓰기 501개 batch도 허용했다. 공식 한도 문서에는 요청 크기 10MiB, 트랜잭션 270초가 있고 쓰기 개수 상한은 명시되어 있지 않다. 운영 적용 전에 테스트용 프로젝트에서 다시 확인해야 한다.
- Android SDK: 검증은 JS SDK(Node)로 했다. Android SDK는 기본으로 디스크 캐시를 쓰므로 앱을 다시 실행해도 대기 쓰기가 남아 재연결 시 보내질 수 있다. 트랜잭션 재시도 횟수와 오류 코드도 Android에서 확인해야 한다.
- 실제 주행 경로에서 칸 목록을 만드는 방법(경로 단순화, 칸 중심 포함 판정), 처리 시간, 실제 차량 수에 따른 경합 정도, 비용 추정은 하지 않았다. S2·요약 문서 방식은 실측하지 않았다.

## 기획 결정이 필요한 항목

1. **획득 단위**: 격자로 할지, 정확한 도형으로 할지. 격자라면 칸 크기(geohash7 약 121m x 152m 권장, geohash8은 칸 수가 약 32배)와 좌표 체계(geohash, S2, 지역 미터 격자).
2. **획득 인정 조건**: 시작점과 종료점 사이 최대 거리, 최소 면적 또는 최소 칸 수, 한 번의 최대 칸 수(트랜잭션 한 번에 499칸 이하로 할지, 나눠 낼지), 경로 끊김 허용 시간, 칸 포함 판정(중심 포함, 일부 겹침).
3. **충돌 우선순위**: 서버에 먼저 커밋된 획득이 이기는지(현재 검증 동작은 나중에 커밋된 획득이 덮어씀), 주행 완료 시각 기준인지. 오프라인 동안 늦게 제출된 획득이 그 사이 다른 사용자의 더 최근 획득을 빼앗아도 되는지.
4. **탈취 규칙**: 다른 사용자의 칸을 언제나 빼앗을 수 있는지, 보호 시간이나 재탈취 대기 시간이 있는지, 자기 칸을 다시 획득하면 시각을 갱신하는지.
5. **오프라인 제출 기한**: 끊긴 동안 만든 획득을 언제까지 인정할지(예: 24시간), 앱 삭제·익명 계정 분실 시 소유 칸 처리.
6. **면적과 순위**: 칸 수로 표시할지 m²로 표시할지, 전체 순위가 필요한지, 순위 갱신 주기(실시간이 필요하면 서버 작업 필요).
7. **이력과 보관**: 획득 기록 보관 기간, 빼앗긴 사람에게 알림이 필요한지, 이력에 이전 소유자를 남길지.
8. **위조 대응**: 클라이언트가 보낸 칸을 그대로 믿을지, Cloud Functions 등 서버 검증을 도입할지. 서버 검증 없이 운영하면 누구나 임의의 칸을 획득할 수 있다.
9. **지도 범위**: 지도에 보여 줄 최소 축척과 한 화면 최대 읽기 수, 실시간 구독 여부(구독은 변경된 문서마다 읽기 과금).

규칙이 정해지면 후보 계약을 `firebase/firestore.rules`와 문서에 반영하고 테스트 프로젝트에서 확인한 뒤 사용자 승인을 받아 운영에 배포한다.
